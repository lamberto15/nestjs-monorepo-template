# Pulling template updates

A project built on this template keeps taking its updates: fixes, security
patches, new platform modules. The template publishes them as releases (`v*`
tags with notes, [releases](releases.md)); a project merges a release tag the
way it merges any branch. This is a git merge, not a generator: your changes
and the template's meet in the same files, and git keeps both.

## Starting a project so that updates merge

Clone the template, keeping its history, and make your own repository the
`origin`:

```bash
git clone https://github.com/lamberto15/nestjs-monorepo-template my-app
cd my-app
git remote rename origin template        # the template stays a remote
git remote add origin git@github.com:<you>/my-app.git
git push -u origin main
git push origin --tags                   # optional: the template's release tags
```

With the shared history, a later `git merge v1.4.0` brings exactly what the
template changed since the version you started from.

**A copy without the history** (a downloaded archive, a squashed first
commit, GitHub's "Use this template") shares no commit with the template, so
the first merge would conflict in every file. Record once which release you
started from, without changing any file:

```bash
git remote add template https://github.com/lamberto15/nestjs-monorepo-template
git fetch template --tags
git merge --allow-unrelated-histories -s ours v1.2.0 -m "chore: record template v1.2.0 as merged"
```

`-s ours` keeps your tree as it is and tells git that v1.2.0 is in it; from
then on, merges bring only what changed after v1.2.0. Pick the release you
copied (by date: `git for-each-ref --sort=creatordate
--format='%(creatordate:short) %(refname:short)' 'refs/tags/v*'`); if you
started between two releases, record the commit you copied instead of a tag.

## Taking a release

Read the release's notes first ([the Releases page](https://github.com/lamberto15/nestjs-monorepo-template/releases)):
its breaking changes, its migrations (and whether the release before it runs
on them), new variables, the typed client's version. Then, in your project,
the usual way (a branch, a pull request, CI; [development](development.md),
"Git workflow"):

```bash
git fetch template --tags
git switch -c chore/template-v1.3.0 origin/main
git merge --no-edit v1.3.0                # always a merge commit: "Merge tag 'v1.3.0'"
# resolve the conflicts (below), then:
pnpm install
pnpm build && pnpm lint && pnpm test && pnpm test:e2e
pnpm db:check && pnpm client:check
git push -u origin HEAD                   # a pull request, CI, review
```

- **One release at a time** when a release's notes list destructive
  statements (a contract step: dropping what an earlier release stopped
  using). Expand/contract assumes the expand release was deployed before the
  contract one ([pitfalls](pitfalls.md), "Migrations: expand/contract"); a
  rollback goes back one release only. Releases without them can be merged
  several at once (merge the newest tag).
- **Merge, don't rebase or cherry-pick:** the merge records which release you
  have, so the next one brings only its own changes.
- **What changed in a file:** `git log v1.2.0..v1.3.0 -- <path>` and
  `git diff v1.2.0 v1.3.0 -- <path>`.
- **Remember resolutions:** `git config rerere.enabled true` replays a
  conflict's resolution when the same conflict comes back (a file you
  changed the same way every time).
- The commit-msg hook lets merge commits through; your pull request's title
  is checked as usual (`chore: template v1.3.0`).

## Conflicts

| Where | What to do |
| --- | --- |
| `apps/api/drizzle/` | Read [the migrations](#the-migrations) below: never hand-edit a snapshot |
| `pnpm-lock.yaml` | Take either side, then `pnpm install` regenerates it: `git checkout --theirs pnpm-lock.yaml && pnpm install` |
| `packages/api-client/openapi.json`, `src/schema.ts` | Generated: resolve the routes first, then `pnpm client:generate` |
| `apps/web/src/routeTree.gen.ts` | Generated by the router's plugin: resolve the routes first, then `pnpm build` rewrites it |
| `packages/api-client/package.json` (version), `CHANGELOG.md` | Your client's version and changelog are your own once you publish it: keep yours (`git checkout --ours`). |
| `docs/roadmap.md`, `README.md`, `AGENTS.md`, `CLAUDE.md` | Yours: keep your side, take what you want of the template's |
| `env.example`, `docs/configuration.md` | Keep both sides' variables; the release notes list the new ones |
| `app.module.ts`, `schema.ts`, feature registrations | Keep both: your features and the template's modules sit side by side |
| The example feature you removed (`features/notes/`, `test/features/notes/`, and the web app's `apps/web/src/features/notes/` and `apps/web/src/routes/_app/notes/`): "deleted by us, modified by them" | Keep it removed (`git rm -r` those paths). A release migration that changes the `notes` table can't run on your database, which dropped it: the release notes flag it, and [the migrations](#the-migrations) say how to take a release's migrations |
| `compose*.yaml`, `.github/workflows/` | Take the template's unless you changed them, then merge by hand; CI checks Compose's secrets and images |

A file you deleted and the template changed comes back as a conflict
(`deleted by us`): `git rm <file>` keeps it deleted.

### Code written for Express

The API moved from Express to Nest's native `node:http` adapter
(`@nestjs/platform-node`; [architecture](architecture.md), "The HTTP
server"). Code of your own that a merge leaves on Express:

- **`import type { Request, Response } from 'express'`**: take
  `NodeRequest` and `NodeResponse` from `@nestjs/platform-node`; the
  Express helpers the template uses (`req.ip`, `req.get()`, `res.cookie()`,
  `res.redirect()`, `res.set()`, `res.type()`) are there.
- **`NestExpressApplication`**: `NestNodeApplication`. Create the app with
  `createHttpAdapter()` (`core/http/http-setup.ts`), as `main.ts` and
  `test/support.ts` do.
- **`FileInterceptor` and the other upload interceptors** come from
  `@nestjs/platform-node`; pass `uploadToDisk()` the injected `StorageDisk`
  (`disk`), as the template's upload interceptors do.
- **`req.route`** isn't set: `matchedRouteKey(req)` (`core/http/route-key.ts`)
  names the matched route.
- **Express-only middleware** (one that reads `req.app.settings`, Express's
  router, or a helper the adapter lacks) needs a replacement; plain
  connect-style `(req, res, next)` middleware, like `compression`, works.
- **A string type set on a response** (`@Header('Content-Type', …)`,
  `res.type()`) gets no `; charset=utf-8` added: write it out where clients
  expect one. Paths are case-sensitive, and a path parameter over 2048
  characters is a 414.

Then `pnpm remove @nestjs/platform-express @types/express` in `apps/api`
once nothing imports them.

### The migrations

Drizzle 1.0's migrator applies every migration (`apps/api/drizzle/<timestamp>_<name>/`)
a database doesn't have, whatever its timestamp. Each `snapshot.json` names
the one before it, so `pnpm db:check` (`drizzle-kit check`) sees when
two lines of migrations touch the same tables. The template's migrations
were generated before you merged them, so:

- **No migrations of your own since your last template merge:** the
  template's merge cleanly (new folders) and apply in order. Keep them.
- **Migrations of your own since then:** keep both sides' folders and run
  `pnpm db:check`. When it passes, both apply. When it reports a conflict,
  don't merge them: take your side of the folder, then generate the
  template's schema changes as a migration of your own (its `*.tables.ts`
  changes came with the merge):

  ```bash
  git restore --source=HEAD --staged --worktree -- apps/api/drizzle   # your migrations only
  pnpm db:generate                                                    # one new migration: the template's changes
  pnpm db:check
  git add apps/api/drizzle && git commit                              # concludes the merge
  ```

  The migration is generated, as every migration is, and CI's
  `migration-lint` checks it like any other. It holds the same statements as
  the template's, so the release notes' expand/contract findings apply to it.
- **Never edit a migration you already deployed**, theirs or yours: change
  the tables and generate a new one.

### Drizzle 1.0

The release with drizzle-orm and drizzle-kit 1.0 moved `apps/api/drizzle/`
(and `test/fixtures/drizzle/`) from drizzle-kit 0.x's layout (`NNNN_<name>.sql`,
`meta/_journal.json`, `meta/NNNN_snapshot.json`) to 1.0's, with
`drizzle-kit up`: `<when>_<name>/migration.sql`, where `<when>` is the
journal's `when` to the second (UTC) and the SQL is byte for byte the same.

- **Your databases need nothing by hand.** The first `migrate` of the
  release adds `name` and `applied_at` to `drizzle.__drizzle_migrations`
  (and the tests' `__drizzle_fixture_migrations`), names each row after its
  folder (matched on `created_at` to the second, then on the file's
  sha256) and applies nothing again (`test/migrations-upgrade.e2e-spec.ts`).
  A row it can't match (a migration edited after it was applied) fails the
  migrate. Deploy the last 0.x release first, so every
  database has applied the migrations the upgrade knows.
- **Migrations of your own:** convert them as the template did, before you
  merge the release, on your side alone. drizzle-kit 1.0.0-rc.5's `up`
  refuses or misreads a few strings older snapshots hold, so the template
  rewrote them in its old `meta/*_snapshot.json` first (scripted; never
  in a `.sql`), one commit each:
  1. a foreign key's `"onDelete": "set null (\"col\")"` (PostgreSQL 15's
     column list) to `"set null"`: `up` stops at it;
  2. a column type `timestamp (N)` to `timestamp(N)`, and the
     `"<table>".` qualifier dropped from an index's `where` and a check's
     `value` on that same table;
  3. an index `where` that is only `"col" is null` (or `is not null`)
     wrapped in parentheses, as 1.0 writes `isNull()`.

  The last two change nothing in the database, but without them the
  converted snapshots differ from what 1.0 reads in your tables, and the
  next `db:generate` rewrites hundreds of columns, indexes and checks.
  Then `pnpm --filter <api> exec drizzle-kit up` (with
  `--config=drizzle.fixtures.config.ts` for the fixtures), and check:
  every `migration.sql` hashes as its old `.sql`, `pnpm db:generate` and
  `db:generate:fixtures` write nothing, `pnpm db:check` passes, and
  `drizzle-kit push --explain` on a database built from the migrations
  reports no changes. Then merge the release: the template's folders are
  the ones `up` made of the same files.

## Deploying the update

A database from before organizational units (#595) must run the release that
introduced them first: later releases no longer rewrite the team-era names
rows store, and their migrate fails if one is left ([releases](releases.md),
"Upgrading across a removed rename").

As any release of your project ([deployment](deployment.md)): the migrations
run first, while the previous release still serves. Check the release notes'
"Rolling back" section before deploying: rolling back is rolling the image
back, and works only while every migration in between follows expand/contract.
